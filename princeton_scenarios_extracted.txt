Data Platform Modernization
Proof of Concept — Test Scenario Catalogue
Vendor Preparation Guide
1. Purpose & Instructions for Vendors
This document defines the Proof of Concept (POC) test scenarios Princeton’s Data Management, Integration, and Analytics (DMIA) team and Business Partners will use to evaluate candidate data platform solutions. Each scenario reflects a real operational requirement drawn from our current data engineering, analytics, and business user workflows.
Vendors are asked to:
Review every scenario in this catalogue and prepare a structured demonstration plan that maps each scenario to a specific capability or feature within your proposed solution stack.
Indicate where your solution fully satisfies a scenario, partially satisfies it, or addresses it through a workaround or partner integration.
Create a playbook and/or supply a technical resource that will guide members of the DMIA team in building and executing each demonstration during the scheduled POC sessions.
Provide sample code, configuration screenshots, or pipeline artifacts in advance where possible so that sessions can focus on depth rather than setup.
Note any scenario that cannot be demonstrated and explain why.
If a scenario can be demonstrated with both a code and no-code/low-code options; have both available.
The scenarios are grouped by four user personas that represent the full range of stakeholders who will interact with the new platform. Vendors must address all four persona groups.
2. User Personas
Persona 1 — Software / Data Engineer
Current skills profile: Oracle SQL (including PL/SQL), enterprise ETL tool development, Python scripting, Linux bash scripting, REST API integration, SFTP automation. Responsible for building and maintaining data pipelines, orchestrating job schedules, and managing platform operations.
Persona 2 — Data Scientist / Advanced Analyst
Current skill profile: SQL, Python, R, statistical modelling, machine learning experimentation. Requires direct access to data in the platform, notebook-style development environments, and the ability to blend ingested data with their own analytical datasets.
Persona 3 — Business Analyst
Current skill profile: Limited or no SQL nor coding languages. Comfortable with Excel and standard reporting tools. Needs to independently access pre-loaded data, enrich it with spreadsheet uploads, perform light transformation, and produce flat-file or spreadsheet outputs for internal and external distribution.
Persona 4 — Platform Administrator
Current skill profile: Linux scripting for file manipulation and SFTP. Handles platform and software security access. Knowledge in installing applications in both Linux and Windows environments. Handles software package administrative duties applying security patches and installing fix packs. Uses SQL skills to create and maintain Oracle FGAC (Fine Grained Access Control)  policies and packages to enforce row and column level security.

The platform must support connectivity to the breadth of source systems our pipelines currently consume. Demonstrate each of the following connection types within your proposed solution.

SE-18

Transpose a dataset from a long (rows) format to a wide (columns) format, and demonstrate the reverse operation.

Only the last record per group is flagged; all others are correctly marked or excluded.

Output contains one summary row per group with correctly accumulated values.

6. Persona 4 — Platform Administrator Test Scenarios
The Platform Administrator is responsible for the health, security, and cost efficiency of the data platform across all environments. The following scenarios validate that the platform provides adequate tooling for access governance, data security, compute management, and financial accountability.
6.1 User & Group Access Management
Demonstrate how the platform manages identity, roles, and permissions across environments and data assets.
#
Test Scenario
What to Demonstrate
Expected Outcome
PA-01
User provisioning and role assignment
Create a new platform user, assign them to one or more predefined roles (e.g. read-only analyst, pipeline developer, admin), and demonstrate that access is immediately enforced.
User can access permitted objects and is blocked from restricted ones; no manual permission grant required beyond role assignment.
PA-02
Group-based access control
Create a user group, assign permissions to the group rather than to individuals, add and remove users from the group, and verify that permissions propagate automatically.
Permissions reflect group membership in real time; removing a user from a group revokes access without additional steps.
PA-03
Environment-level access segregation
Demonstrate that a developer granted access to a development environment cannot access production data or pipelines without explicit elevation of their permissions.
Dev user cannot read, write, or trigger anything in the production environment; access boundary enforced at the platform level.
PA-04
Source and target object-level permissions
Restrict a specific user or group to a subset of source connections or target datasets — e.g. grant read access to one database schema but not another.
User can connect to permitted objects; connection attempt to a restricted object returns a permission error, not a data result.
PA-05
Permission audit trail
Produce an audit report or log showing who was granted or revoked what access, by whom, and when.
Audit log queryable or exportable; each entry contains actor, action, target object, and timestamp.
PA-06
Service account and API credential management
Create and manage credentials for automated pipeline service accounts separately from human user accounts. Demonstrate credential rotation without pipeline downtime or notification of expiring credentials
Service account credentials rotatable; pipelines continue running during and after rotation with no manual intervention or notification of manual key rotation required.
6.2 Row-Level and Column-Level Security
Data security must be enforceable at the field and record level without requiring separate physical copies of datasets.
#
Test Scenario
What to Demonstrate
Expected Outcome
PA-07
Column-level security — masking sensitive fields
Configure a policy that masks sensitive columns (e.g. SSN, salary, date of birth) for restricted roles. Demonstrate that a permitted user sees the full value while a restricted user sees a masked or null result from the same query.
Masked user receives redacted output; unmasked user receives full values; no separate table or view required.
PA-08
Column-level security — full column restriction
Restrict a column entirely so it is absent from query results for a designated role — not masked, but not returned at all.
Restricted column absent from query results for the restricted role; no error thrown, column simply excluded.
PA-09
Row-level security — attribute-based filtering
Apply a row-level security policy so that a user or group sees only the rows relevant to them (e.g. a department user sees only their department’s records) without the query needing an explicit WHERE clause.
User A and User B run the same query; each receives only the rows their policy permits; neither receives the other's data.
PA-10
Row-level security — dynamic policy based on user identity
Implement a dynamic RLS policy where the filter condition is derived from the logged-in user's identity or group membership at query time, not a hard-coded value.
Policy evaluates at runtime; adding a user to a group automatically applies the correct row filter without modifying the policy.
PA-11
Security policy testing and validation
Demonstrate a method for an administrator to test that security policies behave as intended before rolling them out to production. Similar to Oracle’s “faux user”
Administrator can impersonate or simulate a given role and verify the restricted view without exposing real data.
PA-12
Security policy audit and documentation
Show how active row and column security policies are inventoried — which policies apply to which tables, and which roles are affected.
All active policies visible in a central location; each policy linked to the tables and roles it governs.
